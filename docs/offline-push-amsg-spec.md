> 基于 ReiStandard 主动消息 API 的分层实现
> 
> 投递层下沉到标准，自有部分收敛为「存快照 · 判定触发 · 编排请求」。

> **致谢**：投递层完整采用 [Tosd0/ReiStandard](https://github.com/Tosd0/ReiStandard)（MIT）标准及其官方实现包

> **宿主**：float（AGPL-3.0）。触发策略以纯函数钩子形式隔离，可独立替换。全部密钥与地址使用占位符。

## 0 范围与基线

**致谢**：本方案的投递层——推送协议、载荷加密、双通道投递、去重与送达裁决——完整采用 ReiStandard 主动消息 API 标准及其官方实现包（MIT），谨向作者致谢。

仓库：https://github.com/Tosd0/ReiStandard

### 0.1 交付目标

| 能力 | 触发 | 页面关闭后 |
|------|------|-----------|
| A · 定时主动推送 | 服务端调度到点 | 可独立运行。服务端持有加密快照，自行调用模型并投递 |
| B · 后台回复接管 | 用户发起请求后页面隐藏 | 可完成已接管的请求。结果经推送回到设备并落盘 |

### 0.2 技术基线

| 层 | 选型 | 许可 | 职责 |
|----|------|------|------|
| 投递层 | ReiStandard AMSG | MIT | VAPID、载荷加密、双通道投递、去重、送达裁决 |
| 宿主 | float 上游 main | AGPL-3.0 | 会话、角色、提示词组装、消息落库 |
| 调度层 | 本方案定义 | 随宿主 | 快照存储、触发判定、请求编排 |

使用的 AMSG 包：

- `@rei-standard/amsg-shared` — wire shape 与类型守卫
- `@rei-standard/amsg-instant` — 无状态投递 worker
- `@rei-standard/amsg-client` — 页面侧客户端与送达裁决
- `@rei-standard/amsg-sw` — Service Worker 运行时

标准文本与各包源码见 https://github.com/Tosd0/ReiStandard

**权威来源声明**：本文引用的标准字段与行为均以仓库内 `standards/` 两份规范与各包 README 为准，文中关键请求体（4.5）已对照 amsg-instant README 逐字段核实。

**实现前必读三份材料**：amsg-instant README（请求 schema、handler 配置、钩子契约）、amsg-sw README（SW 接入与消息协议）、amsg-client README（deliver() 与送达裁决）。本文不复述它们的完整 API——文档演进以包为准。

### 0.3 分层原则

标准负责「怎么送」，本方案负责「何时发起、发什么内容」。

投递、加密、重试、去重、送达判定全部下沉到 AMSG；触发策略与提示词内容属于业务层，本方案只定义它的接入点与数据契约，不规定策略本身。

> 这条线一旦模糊，就会出现在标准钩子里堆业务逻辑的写法，两边都无法独立演进。

## 1 架构

### 1.1 分层数据流

```
┌─ 调度服务（常驻，本方案定义）──────────────────────┐
│  存储：加密快照 · 下次触发时间 · 订阅端点 · 决策状态 │
│  cron 到点 → 解密快照 → 调用决策钩子                 │
│            → 渲染 messages 数组 → 发起投递           │
└──────────────────┬───────────────────────────────────┘
                   │ POST /instant
                   │ { apiUrl, messages, subscription, hooks 上下文 }
                   ▼
┌─ 投递层（amsg-instant，无状态）─────────────────────┐
│  调模型 → onLLMOutput 钩子分段 → 构造 AmsgPush       │
│  VAPID + aes128gcm → SSE 直送 ‖ Web Push 备份        │
└──────────────────┬───────────────────────────────────┘
                   ▼
┌─ 客户端（amsg-sw + 本方案收件箱）───────────────────┐
│  push/SSE → 按 messageId 去重 → 收件箱落盘 → 通知    │
│  页面恢复 → drain → 宿主消息解析器 → 会话落库        │
└─────────────────────────────────────────────────────┘
```

### 1.2 服务端路径选型

AMSG 提供两条服务端路径，需先定型：

| 路径 | 形态 | 调度模型 | 状态 |
|------|------|---------|------|
| amsg-server | 多租户，需数据库 | 预置任务：创建时写入提示词，cron 到点调模型 | 有状态 |
| amsg-instant | 单文件 worker | 即时：调用即发，不含调度 | 无状态 |

**选型：投递用 amsg-instant，调度与决策留在自有服务。**

amsg-server 的提示词在创建任务时固化。要让它拿到最新上下文，必须在每次上下文变化时 update-message 整体覆盖任务——这与自有的快照同步等价，却额外背上多租户模型与「每租户独立数据库 URL」的硬约束。

而本方案的触发判定依赖到点那一刻的实时状态（见 4.3），预置任务模型无法表达。

**附带收益**：自有服务中不再包含任何推送发送代码。VAPID 签名、aes128gcm 加密、TTL 装配、订阅失效处理全部由 amsg-instant 承担。自有部分退化为「存快照 + 判定 + 编排请求」，代码量与出错面显著下降。

### 1.3 两条能力线

| 能力 | 发起方 | 是否经过决策钩子 | messages 来源 |
|------|-------|----------------|--------------|
| A · 定时主动 | 调度服务 cron | 是 | 服务端用快照渲染 |
| B · 后台回复 | 页面交接 → SW 出站队列 | 否 | 页面直接复用主聊天已组装的消息体 |

两条线共用投递层与客户端收件箱，差异仅在发起方与是否需要决策。能力 B 不经过决策钩子——用户已明确要一个回复，不存在「该不该发起」的判断。

## 2 与 AMSG 的契约映射

### 2.1 推送 wire shape

AMSG 的推送是以 `messageKind` 为字面量判别器的联合类型，由三个正交维度加一个路由来源描述：

| 轴 | 字段 | 取值 | 由谁定 |
|----|------|------|-------|
| Dispatch | messageType | instant / fixed / prompted / auto | 标准（固定枚举） |
| Business | messageSubtype | 任意字符串 | 调用方自由命名 |
| Content | messageKind | content / reasoning / tool_request / error | 标准（固定枚举） |
| 路由 | source | instant / scheduled | 标准 |

走 amsg-instant 时 `messageType` 与 `source` 恒为 `instant`。共有字段中与本方案相关的是 `messageId`（每条唯一）、`sessionId`（同一 LLM 轮次内共享，含自动发出的 reasoning 与后续内容分段）、`metadata`（调用方透传，标准包不得写入）。

### 2.2 业务语义落点

| 本方案概念 | 落到 | 说明 |
|-----------|------|------|
| 能力线与触发原因 | messageSubtype | 建议用点号分层命名，便于客户端前缀匹配 |
| 角色标识 | metadata.charId | 客户端据此把消息路由到正确会话 |
| 来源标记 | metadata.origin | 标记为服务端产出，供客户端避免自激（见 5.5） |
| 一轮 LLM 的归属 | sessionId | 客户端据此把 reasoning 与内容分段拼成一轮 |
| 分段顺序 | messageIndex / totalMessages | 由标准在 ContentPush 上给出 |

`metadata` 是标准明确规定的调用方透传字段，包不得写入——这是放置私有语义最安全的位置，不会与标准后续版本抢字段。

`messageSubtype` 是自由命名的业务命名空间，标准不做校验。

### 2.3 提示词字段

标准对 AI 消息字段的约束中，与本方案直接相关的三条：

| 字段 | 约束 | 本方案取值 |
|------|------|----------|
| apiUrl | 必填，可 `new URL()` 解析。实现方对 OpenAI 风格路径做幂等补全 | 由快照携带。传完整 `…/chat/completions` 可绕开补全 |
| completePrompt / messages | 互斥二选一，同时给或都不给均报 400 | 一律用 messages |
| temperature | messages 路径未传时不发，由上游主路径决定 | 不传，与前台一致 |

`messages` 数组由 handler 原样转发给 LLM，不做注入或重排，与主聊天路径调用 LLM 的 body 字节级一致。

这是本方案能保证「离线消息与前台表现一致」的协议级依据：只要服务端渲染出的 messages 与前台组装器同源，模型看到的输入就完全相同。

> 反过来说，任何在服务端另写一套提示词拼接的做法都会破坏这个保证。

### 2.4 分段

宿主的角色回复是多条短消息。标准提供两种切分方式：

| 路径 | 方式 | 适用 |
|------|------|------|
| amsg-server | 任务上带 splitPattern（正则 source 字符串，无 flag，支持数组级联） | 切分规则能用正则表达时 |
| amsg-instant 0.8.0+ | 请求级旋钮已移除。在 onLLMOutput 钩子内调用业务自己的 split 函数，返回完整 pushPayloads | 规则复杂时 |

本方案走 amsg-instant，因此分段在钩子内完成。宿主的分条规则涉及表情标签、媒体指令、状态值段落，超出单条正则的表达能力，钩子路径是唯一可行方式。标准另提供纯工具函数用于保护代码块等不被切碎。

### 2.5 思维链

标准规定：LLM 返回非空 `reasoning_content` 时必须先发一条独立 `ReasoningPush`，再发该轮内容分段，两者共享 `sessionId`。`ReasoningPush` 不带 `messageIndex / totalMessages`。

| 场景 | 建议 | 理由 |
|------|------|------|
| 能力 A · 定时主动 | 在投递 worker 的 handler 配置中关闭：`createInstantHandler({ autoEmitReasoning: false })` | 思维链对用户无价值，且占用推送预算。注意这是 handler 配置项，不是请求字段 |
| 能力 B · 后台回复 | 保留默认 | 若前台本就展示思维链，保持一致 |

### 2.6 送达裁决

标准明确规定 transport 成功不等于送达。

HTTP 200 与 SSE enqueue 成功只说明「发出去了」；反过来 SSE 断开也不等于没送达——Web Push 备份可能已到，iOS 上后台 fetch 被杀是常态。

amsg-instant 0.9.0+ 默认强制开启 Web Push always-on backup：同一条业务消息总是同时走两条通道，由 SW 端按 `messageId` 去重收敛。

裁决由调用方提供的 out-of-band 观察通道完成。amsg-client 的 `deliver()` 返回五种结果：

| 结果 | 含义 | 本方案处理 |
|------|------|----------|
| delivered | 客户端确认落盘 | 唯一算送达的结果 |
| cancelled | 调用方主动取消 | 清理本地 pending 状态 |
| timeout | 未在窗口内观察到 | 不得据此重发，标记为不确定 |
| send-failed | transport 明确失败 | 可按退避重试 |
| completed-unconfirmed | 流程走完但未观察到确认 | 同 timeout 处理 |

## 3 快照同步协议

调度服务常驻在服务端，而角色上下文只存在于用户设备。本章定义两者之间的同步协议。

### 3.1 快照内容

```
身份    charId / charName / userName
上下文  persona        —— 宿主主聊天路径组装出的全部 system 段
        personaHash    —— persona 的 SHA-256，增量协议用
        recentMessages —— 最近若干条纯文本，不混入 persona
场景    见面摘要 / 是否仍在场景中 / 最后一次互动时间
节奏    免打扰时段 / 角色时区（IANA 名）
模型    apiUrl / apiKey / model
版本    snapshotVersion —— 单调递增
```

### 3.2 构建约束

| 约束 | 取值 | 原因 |
|------|------|------|
| persona 来源 | 宿主主聊天提示词组装器 | 与 2.3 的字节级一致要求配套。另写一套拼接会破坏一致性保证 |
| persona 上限 | 约 24 000 字符 | 超限时保头保尾：前段 + 省略标记 + 末段。格式规则通常位于末尾，直接截尾会破坏输出格式 |
| persona 缓存 | 10 分钟 TTL | 完整组装含记忆检索，开销大，不能每次同步都跑 |
| 聊天条数 | 30 条以内 | 先按会话自身的「进入模型条数上限」截断，再套硬上限 |
| 头像 | 仅 https: | data: URL 会把快照撑到 MB 级。标准侧对 avatarUrl 亦只接受 https: |
| 模型协议 | OpenAI 兼容 | 投递层按 OpenAI 风格 chat/completions 调用（见 2.3 的 apiUrl 补全规则）。角色绑定的是非兼容协议时，在快照构建阶段即拒绝并明确提示，不让它上传后在服务端静默失败 |

### 3.3 增量上传

persona 占二十几 KB，聊天增量仅数 KB。全量重传既浪费，也会撞上页面卸载时的请求体配额。

```
客户端：按角色记录「已被服务端确认的 personaHash」
  hash 未变 → 省略 persona 正文，只传 hash
  hash 已变 → 携带完整 persona

服务端：请求缺 persona 时
  hash 与已存快照一致 → 续用旧 persona，正常入库
  不一致或无旧快照     → 返回「需要 persona」

客户端收到「需要 persona」→ 立即以全量重发一次
```

页面转后台时的补传必须走 keepalive 请求，且体积必须小。

> 浏览器对 keepalive 请求体有配额，且同一时刻所有此类请求共享该配额，超限直接抛错——而此时页面往往已无法处理异常。
>
> 增量协议的主要收益不是省流量，而是让锁屏前的补传永远走得通。

### 3.4 并发与版本

- `snapshotVersion` 单调递增，服务端拒绝低于当前值的写入。多标签页并发上传时这条是必需的。
- 换服务端地址或重建订阅后，客户端必须清除本地已确认的 hash 记录，下一轮重新全量上传。
- 快照整体加密后存储，加密失败拒绝保存，不做明文降级。

### 3.5 同步触发

| 触发 | 动作 | 节流 |
|------|------|------|
| App 启动 | drain 收件箱 → 全量同步 | — |
| 定时兜底 | 全量同步 | 分钟级（建议 2 分钟） |
| 上下文变更（消息落库 / 场景结束） | 仅同步该角色 | debounce 约 10 秒 |
| 页面转后台 | keepalive 小包补传 | 增量协议保证是小包 |
| 页面恢复可见 | drain 收件箱 | — |
| 手动同步 | 全量同步 | 用户显式触发 |

> **必须处理一个竞态**：转后台的 keepalive 补传可能撞上正在进行的常规同步。
>
> 不得静默丢弃。正确做法是把后到的请求合并进一个待跑槽位（keepalive 标记取并集），当前同步结束后补跑。被丢掉的恰好是最关键的那一包——用户正在离开。

## 4 调度服务

唯一的自有服务端组件。职责收敛为三件事：存快照、判定何时触发、编排投递请求。不含任何推送发送代码。

### 4.1 接口

| 路径 | 方法 | 用途 |
|------|------|------|
| /health | GET | 健康检查与能力声明（公开） |
| /subscribe | POST | 注册或更新角色调度：订阅端点、间隔区间 |
| /snapshot | POST | 写入加密快照，支持 hash 增量（见 3.3） |
| /snapshot-status | POST | 查询快照版本与 persona 是否在库 |
| /unsubscribe | POST | 删除单角色或该端点的全部调度 |
| /heartbeat | POST | 活跃度上报与对账，返回客户端需补发的项 |
| /test | POST | 测试投递，带可识别标记，不进入会话 |

除 /health 外全部校验调用方令牌。令牌为轻量门槛，不替代身份系统——服务为单人自部署设计。

### 4.2 数据模型

```
schedule (主键: endpoint + charId)
  endpoint / p256dh / auth        订阅三元组
  intervalMs / maxIntervalMs      间隔区间，触发时在区间内随机
  nextFireAt                      下次触发时刻
  leaseUntil                      认领锁，防并发 cron 重复处理
  snapshotCipher / snapshotIv     加密快照
  snapshotVersion / personaHash   版本与增量校验
  snapshotUpdatedAt               陈旧度判定依据
  lastHeartbeat                   活跃度判定依据
  decisionState                   决策钩子的持久化状态（见 4.4）
  lastAttemptAt / lastError / failCount / lastSentAt
```

persona 可按 hash 单独存表，供多个调度共享同一份正文，避免重复存储。

### 4.3 触发流程

```
cron 到点
  ① 取 nextFireAt <= now 且未被认领的调度，数量设上限
  ② 条件更新写 leaseUntil 认领；受影响行数为 0 说明被其他实例抢走，跳过
  ③ 活跃度与成本护栏检查，不通过则顺延
  ④ 解密快照；陈旧度超阈值时降频或跳过
  ⑤ 调用决策钩子（见 4.4）
       → skip(retryAfterMs)  顺延，不投递
       → send(messages, meta) 继续
  ⑥ 组装 /instant 请求体并发起投递
  ⑦ 成功：更新 lastSentAt，在间隔区间内随机 nextFireAt，清 lease
     失败：failCount++，指数退避顺延，记录脱敏错误
```

> 第 ② 步的认领必须是条件更新，不能先读后写。
>
> 每分钟粒度的 cron 在实例重叠或重试时会并发命中同一行，非原子认领会导致同一次调度产出两条消息。

### 4.4 决策钩子

「此刻该不该发起、发什么」属于业务策略，本方案不规定其内容，只定义契约。策略实现可独立演进，不影响调度与投递。

```
输入（钩子只读）
  snapshot        解密后的快照
  schedule        间隔、上次发送时间、逾期程度
  decisionState   上一次决策留下的状态（由钩子自定义结构）
  now             服务端时刻

输出（二选一）
  { action: "skip", retryAfterMs, reason }
  { action: "send",
      messages,        // 直接作为 /instant 的 messages 传入
      messageSubtype,  // 业务命名，落到推送的 Business 轴
      metadata,        // 透传字段，至少含 charId
      nextDecisionState }
```

| 契约条款 | 要求 |
|---------|------|
| 纯函数性 | 钩子不得自行发起网络请求或写数据库；一切外部影响通过返回值表达 |
| 状态持久化 | nextDecisionState 由调度服务写回 decisionState，钩子自身不持有跨次状态 |
| messages 来源 | 必须由快照的 persona 与最近消息渲染，保证与前台组装同源（见 2.3） |
| skip 必须给时长 | retryAfterMs 缺省时调度服务按默认间隔顺延，但会记录一次告警 |
| 幂等 | 同一 (schedule, nextFireAt) 重复调用应产出等价结果，便于重试 |

> 把决策收敛成一个纯函数钩子，是为了让「策略」与「基础设施」能分别测试。
>
> 调度、认领、退避、投递编排可以用假钩子做集成测试；策略可以用固定快照做单元测试，不需要真实推送链路。

### 4.5 投递请求编排

钩子返回 `send` 后，调度服务组装 `POST /instant`。以下字段名已对照 amsg-instant README 核实：

```
POST /instant
Content-Type: application/json
Accept: application/json      ← 显式走纯 Web Push 路径（0.9.0+）：
X-Client-Token: <token>          服务端到服务端的调用没有页面在等 SSE

{
  "contactName": "<角色名>",        // 必填，通知发件人显示名
  "messages": [...],                // 来自决策钩子，原样转发给 LLM
  "apiUrl": "...",                  // 来自快照
  "apiKey": "...",
  "primaryModel": "...",            // 注意字段名是 primaryModel
  "maxTokens": 800,                 // 可选
  "messageSubtype": "...",          // 来自钩子，落到推送 Business 轴
  "metadata": { "charId": "..." },  // 来自钩子，透传到 push payload
  "avatarUrl": "https://...",       // 可选，非法值软清空不报错
  "pushSubscription": {             // 注意字段名是 pushSubscription
    "endpoint": "...",
    "keys": { "p256dh": "...", "auth": "..." }
  }
}
```

两个容易写错的地方，均已对照包文档核实：

1. `autoEmitReasoning: false` 不是请求字段，是投递 worker 的 handler 配置项（`createInstantHandler({ autoEmitReasoning: false })`），放进请求体不生效。
2. `firstSendTime / recurrenceType` 在 amsg-instant 上是非法字段，携带会直接返回 `400 INVALID_PAYLOAD_FORMAT`——调度语义全部由调度服务自持，不下发。

分段在 amsg-instant 的 `onLLMOutput` 钩子内完成（见 2.4）。该钩子由部署方在 worker 侧配置，与调度服务的决策钩子是两个不同的扩展点，不要混淆。载荷超过内联上限时由投递层内建的 multipart / blobStore 机制处理（multipart 默认开启），调度服务无需关心。

### 4.6 护栏

- 单次 cron 处理条数上限，防止积压时一次打爆模型配额。
- 每端点每日投递上限，超限静默停投并在客户端可见。
- failCount 超阈值自动停用该调度，避免对失效配置持续重试。
- 模型调用超时与 maxTokens 上限，共同约束单次成本。
- 快照陈旧度阈值：超过阈值时降频或跳过，避免用过时上下文生成。
- 按 lastHeartbeat 做活跃度分级：活跃正常调度，沉默放大间隔，长期无心跳则休眠（保留记录、停止生成），心跳恢复即自动回到正常档。这是最有效的成本护栏——不给早已不用的设备持续烧钱。

## 5 客户端

### 5.1 Service Worker

使用 `@rei-standard/amsg-sw` 提供的运行时，注册在独立子作用域，不改动宿主已有的根作用域 Service Worker。

> 宿主的根 SW 是活跃维护文件（缓存策略、版本号、离线导航兜底会持续调整）。把推送逻辑并入会造成长期合并冲突。独立注册的代价只是多一个推送订阅。

若 iOS 是必须支持的目标，则改为在宿主 SW 顶部 `importScripts` 引入投递运行时——上游改动时只需保住这一行。

> SW 脚本必须是静态资源根目录下的文件。构建产物目录（带内容 hash 的路径）无法注册更宽的作用域。

### 5.2 前台与后台

标准要求实现前台/后台检测：后台显示系统通知；前台直接在 UI 渲染，并可通过 payload 上的通知显示策略（when-hidden 或关闭）避免重复弹窗。检测方式是在 push 事件中 `matchAll({ type: "window", includeUncontrolled: true })` 并筛出可见客户端。

> **无论前台后台，push 事件都必须调用 `showNotification`**（或由标准运行时代为调用）。
>
> iOS 对不弹通知的推送会撤销订阅；Chrome 会代为显示一条通用通知。把它放进条件分支是错误的——正确做法是用 payload 的显示策略控制，而非跳过调用。

### 5.3 收件箱

标准的 SW 运行时负责去重与通知；本方案在其之上增加一层业务收件箱，承担「落盘 → 页面恢复后写入会话」。

| 环节 | 要求 |
|------|------|
| 存储 | IndexedDB，object store 以 messageId 为 keyPath——重复投递直接覆盖，天然去重 |
| 顺序 | 写入顺序为 落盘 → 广播 → 通知，不得调换 |
| 广播 | SW 位于子作用域、不控制页面，matchAll 必须带 includeUncontrolled，否则找不到窗口 |
| 二层去重 | 页面侧维护最近若干条已处理 messageId 的环形表（建议 500），应对收件箱删除失败或竞态 |
| 通知点击 | notificationclick 由标准 SW 运行时处理；本方案需把 metadata.charId 带进通知的 data，点击后聚焦或新开窗口，页面先 drain 再进入对应会话（冷启动经启动参数传递），否则用户点开通知看到的是一个还没有那条消息的会话 |

### 5.4 drain

```
触发：App 启动 / focus / 恢复可见 / 收到 SW 广播 / 通知点击

① 取跨标签互斥锁（Web Locks），全程持有
② 读出全部收件箱项，按发送时刻升序排列
③ 逐条：
     已在环形表中      → 只清箱
     测试标记 / 空正文 → 只清箱
     找不到对应会话    → 累加重试计数，保留
     正常              → 交给宿主消息解析器落库
④ 落库成功 → 记入环形表 → 删除收件箱项
⑤ 落库失败 → 保留，等下次 drain
```

> **顺序不可颠倒：先落库成功，再删收件箱。**
>
> 反过来会在 drain 中途失败时永久丢消息，且没有任何重试来源。

> **跨标签互斥同样必需**：桌面场景下两个标签同时可见是常态，并发 drain 会重复落库，而环形表是每标签各自持有的，救不了跨标签竞态。

### 5.5 落库与自激

落库交给宿主已有的消息解析入口，由它完成富文本解析、分条写入与后处理。服务端不解析宿主的消息格式，因此不需要跟随宿主格式演进。

> **必须给服务端产出的消息打上来源标记（`metadata.origin`），并在落库时保留。**
>
> 否则宿主页面内已有的主动消息服务会把 drain 进来的消息当作「角色刚说了话」，再排一次后续动作，形成自激循环：每次打开 App 都多出一条消息。

### 5.6 能力 B 的交接

| 时刻 | 条件 | 动作 |
|------|------|------|
| 页面可见 | — | 走宿主原有链路；预热订阅但不发起投递 |
| 页面隐藏 | 本地已产出首字 | 继续本地，不交接 |
| 页面隐藏 | 本地尚无输出 | 启动数秒宽限计时 |
| 宽限期内恢复可见 | — | 取消交接 |
| 宽限到期 | 仍隐藏且无输出 | 交接 |
| pagehide | 本地无输出 | 立即交接，不等宽限 |

> **交接以意图为准，不以结果为准。**
>
> 置位「已交接」的同一刻即放弃本地结果，不要等待出站队列的 ACK 回来再取消——等待期间本地流可能已开始输出，届时用户会同时看到本地半截与服务端完整两份。
>
> ACK 超时视为不确定：既不回滚也不重发，UI 保持 pending，等待送达裁决或下次 drain。

> **请求必须先写入 SW 的出站队列再发起**，且队列项带过期时间。页面隐藏后直接 fetch 有明确风险：页面可能在发包前被冻结，请求根本没有送出，而页面已无法保存状态。过期项在 flush 时丢弃并在 UI 标记，避免用数日前的上下文生成回复。

## 7 部署与配置

### 7.1 组件

| 组件 | 形态 | 需要 |
|------|------|------|
| amsg-instant worker | 无状态函数 | VAPID 密钥对；可选调用方令牌；onLLMOutput 分段钩子 |
| 调度服务 | 常驻或 Serverless + cron | 数据库（快照与调度）；快照加密密钥；调用方令牌 |
| 客户端 | 宿主内新增模块 | SW 静态文件位于资源根目录；订阅与快照同步；收件箱与 drain |

### 7.2 配置项

| 配置 | 位置 | 可否进入前端 |
|------|------|------------|
| VAPID 公钥 | worker + 前端 | 可以 |
| VAPID 私钥 | worker 机密 | 不可以 |
| 快照加密密钥 | 调度服务机密 | 不可以 |
| 调用方令牌 | 服务端 + 前端 | 会存在前端，仅为轻量门槛 |
| 调度服务地址 | 前端配置 | 可以 |
| 模型凭据 | 随快照上传 | 由用户自行提供 |

### 7.3 联调前提

> 宿主仅在生产构建下注册 Service Worker（开发模式直接跳过）。因此推送在开发服务器里完全无法测试，联调必须用生产构建启动，或临时放宽该判断。这一条不提前说明会浪费掉联调的第一天。

- **iOS（16.4+）**：必须先「添加到主屏幕」并从主屏图标启动，Web Push 才可用；每条推送都必须弹系统通知，否则系统会撤销订阅。
- **通知权限**必须由用户点击触发（设置页开关），不要在启动时自动弹——被拒绝后浏览器不再给第二次机会。

### 7.4 信任边界

- 快照在库中加密，但调度服务在调用投递时必须解密——静态加密不等于端到端加密。
- 模型凭据经调度服务与 amsg-instant 到达模型供应商。建议引导使用单独的低配额密钥。
- 推送服务可见投递时间、频率与大小等元数据；内容已加密。
- 标准自身声明：在无常驻独立密钥服务的 serverless 场景下，函数运行时必须可获得解密材料，因此不保证「部署管理员绝对无法解密」。本方案沿用同一边界，需在产品侧明示。

## 8 可靠性与验收

### 8.1 不变量

1. 推送与 SSE 必须先写客户端收件箱，再写业务会话。
2. 业务落库成功后才删除收件箱项。
3. 同一结果的两条通道与所有重试复用同一 messageId。
4. SW 去重与页面环形表构成双层去重。
5. drain 全程持有跨标签互斥锁。
6. 前台已产出输出时不交接；交接置位后立即放弃本地结果。
7. 出站队列 ACK 超时视为不确定，不得直发第二次。
8. 每个 push 事件都必须触达通知调用。
9. 调度认领必须是条件更新。
10. snapshotVersion 单调递增，旧版本不覆盖新版本。
11. 决策钩子的跨次状态只能通过返回值持久化。
12. 订阅公钥轮换后必须退订并重建。
13. timeout 与 completed-unconfirmed 均不触发重发。

### 8.2 验收

#### 8.2.1 链路

- 健康检查与测试投递正常，测试消息弹通知但不进入会话。
- 注册调度后服务端存在对应记录。
- 首次全量快照可上传，库中看不到明文。
- persona 未变时只传 hash；服务端缺 persona 时客户端自动补发全量。
- 旧 snapshotVersion 不覆盖新版本。
- 转后台的 keepalive 补传成功，不因体积超限失败。
- 离线可达窗口：设备断网 → 触发投递 → 数分钟后恢复网络 → 消息仍然到达（验证推送在设备离线期间不被立即丢弃；若投递层暴露 TTL 配置，显式设为小时级）。
- iOS：从主屏启动的 Web App 中完成订阅、接收与通知点击全流程。

#### 8.2.2 核心场景

- 关闭 App（真正关闭）超过一个调度周期，消息主动送达并弹出系统通知。
- 点击通知进入 App，消息在正确会话中，富文本表现与前台一致。
- 发完消息立即锁屏，回复送达且只出现一条。
- 前台、后台、锁屏、杀进程四种状态均验证过。
- 同一 payload 重放两次，会话中只出现一次。
- 桌面双标签同时可见时 drain 不产生重复。
- SSE 先到、推送后到只落盘一次；页面关闭导致 SSE 消失时推送仍能落盘。
- 决策钩子返回 skip 时不产生投递，且按指定时长顺延。
- 并发 cron 下同一调度只投递一次。
- 订阅失效后服务端记录被清理，客户端下次启动重建。
